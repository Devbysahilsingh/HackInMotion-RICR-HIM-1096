# Mobile i18n

Same architecture as web (docs/i18n/): i18next initialized from **shared/i18n** resources (metro `watchFolders` `../shared` + an `@shared` alias in `resolver.extraNodeModules`, mirrored in `tsconfig.json` and `jest.config.js` so editor, bundler and test runner agree — `mobile/metro.config.js` carries the reasoning); language: first-run screen → `PATCH /users/me` sync → AsyncStorage persistence for pre-auth screens; device-locale default (hi→Hindi).
Mobile-specific requirements: permission rationale strings (camera/location) localized **in our own in-context screens** — see the correction below; TTS `language:'hi-IN'` matched to UI language; Devanagari rendering verified on low-end Android (system fonts fine; ⏳ manual device test pending); date/number Intl polyfill if Hermes lacks full ICU (`@formatjs` polyfills — decision at scaffold, noted); text-scaling tolerance to 1.3× (accessibility, ⏳ manual device test pending).
Parity gate + human-verification workflow identical (docs/i18n/translation-strategy.md) — one translation tree serves both surfaces by construction.

## Correction — Expo's `locales` does NOT localize Android permission strings

An earlier revision of this file called for `app.json`'s `locales` config to localize the OS-level permission strings via "Android per-locale resources". **That is wrong and no such block ships.**

- Expo's `locales` key compiles to iOS `InfoPlist.strings` files. It is **iOS-only**. There is no Android leg to it.
- Android's runtime permission sheet text is **generated by the system**, in the system's own language, from the permission group. An app cannot override it. The only app-authored string near it is the optional rationale an app shows *itself*, before or after calling the OS.

Android is the only shipped target (deployment.md), so a `locales` block would have been inert — a config line that reads like a feature and does nothing. `mobile/app.config.ts` therefore carries no `locales` key and a comment saying why.

What the farmer actually reads in their language is our own in-context rationale screen, localized through `shared/i18n` like every other string (`mobile` namespace: `camera.*`, `permission.*`). The plugin-level strings in `app.config.ts` (`expo-camera` `cameraPermission`, `expo-image-picker` `photosPermission`, `expo-location` `locationAlwaysAndWhenInUsePermission`) are the manifest's English descriptions — they are build-time manifest metadata, not a localization surface.

## As built

- **Resources are inlined at bundle time.** `mobile/src/i18n/resources.ts` imports all 34 JSON files (17 namespaces × en/hi) through `@shared`. No runtime fetch, no loading state for text — so the app's own copy works with the network off.
- **Namespace list is closed and identical to the web's** — `common, auth, farm, crop, health, weather, irrigation, landing, market, fertilizer, cropRec, community, voice, errors, agri, disease` — **plus `mobile`**, which holds the copy with no web counterpart (permission rationales, camera guidance, the offline banner, tab labels).
- **`keySeparator: false`.** The canonical files are flat with literal dots inside keys (`schedule.basal.full`). With i18next's default separator the lookup would hunt for a nested object that does not exist, so the key a backend route emits is the key this client resolves, byte for byte. `nsSeparator: ':'`.
- **No language-detector plugin.** The browser detector reads `localStorage`, which does not exist here, and AsyncStorage is asynchronous — a detector would resolve after the first render and flash English at a Hindi speaker. Instead `loadStoredLanguage()` runs once during boot and the resolved value is passed to `init()` as a plain string. Device default comes from `expo-localization`'s `getLocales()[0].languageCode`, region trimmed; anything not shipped falls to `en` — a default, not a claim of support.
- **`escapeValue: false`.** React Native does not interpret markup, so HTML escaping would only mangle ₹ and Devanagari.
- **`fallbackLng: 'en'`** is a safety net, not a strategy (docs/i18n/architecture.md rule 3). The parity gate keeps it from being load-bearing.
- **Zero hardcoded strings, enforced.** `scripts/check-ui-strings.mjs` now scans `mobile/src` alongside `web/frontend/src` and its visible-attribute list gained React Native's `accessibilityLabel`, `accessibilityHint` and `accessibilityValue` — a screen reader speaks those verbatim, so an English literal there is as untranslated as visible text.
